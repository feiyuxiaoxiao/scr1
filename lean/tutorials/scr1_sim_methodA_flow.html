一、整体流程全景图

方式 A 是"零编写"验证——直接运行仓库自带的测试，一条命令搞定。它的完整流程是：

① 编译测试
hello.c → .hex
→
② 编译仿真器
Verilog → C++
→
③ 运行仿真
.hex 被加载执行
→
④ 得到结果
PASS / FAIL

在 SCR1 中，这三步被一条 make 命令串起来：

make TARGETS=hello run_verilator
为什么这条命令会"自动完成全部"
SCR1 的顶层 Makefile 把编译测试和编译仿真器、运行仿真串成了依赖关系：run_verilator 目标依赖 test_info，而 test_info 依赖 tests（即 hello 测试的编译）。所以只要一条命令，make 会按依赖顺序自动执行。

二、前提：环境已就绪

这套环境之前已经搭好，三个关键组件：

组件位置作用
RISC-V 交叉编译器/usr/bin/riscv64-unknown-elf-gcc把 C/汇编编译成 RISC-V 机器码
Verilator/usr/bin/verilator (5.006)把 SCR1 的 Verilog 代码编译成 C++ 可执行仿真器
picolibc 运行时库gcc 安装时附带提供 printf 等基础库函数
唯一的坑：common.mk
sim/tests/common/common.mk 第 15 行的 --specs=nano.specs 对 picolibc 无效，编译会报 cannot read spec file 'nano.specs'。已从该行移除（环境适配 hack，未提交 git）。如果以后从 git 重新拉取，需要再移除一次。

三、第 1 步：编译测试程序（C 源码 → .hex）

当 make 执行到 hello 测试时，它会进入 sim/tests/hello/ 目录，用 common.mk 里的规则编译。编译的原料：

文件作用
sim/tests/hello/hello.c测试源码，只有 6 行（main 里调用 sc_printf）
sim/tests/common/sc_print.c提供串口打印函数 sc_printf（输出到仿真控制台）
sim/tests/common/crt_tcm.S启动代码：设置栈指针、跳转 main
sim/tests/common/link_tcm.ld链接脚本：规定代码段/数据段/栈的地址布局

编译出的三个产物

hello.elf
ELF 可执行文件
→
hello.hex
16 进制指令文件
（testbench 加载这个）
→
hello.dump
反汇编清单
（给人看的）

对应的 gcc 命令（这就是 make 实际执行的东西）：

# 1. 编译 .c / .S 成目标文件 .o
riscv64-unknown-elf-gcc -O3 ... -c hello.c  -o hello.o
riscv64-unknown-elf-gcc -O3 ... -c crt_tcm.S -o crt_tcm.o

# 2. 链接成 .elf（用 link_tcm.ld 决定内存布局）
riscv64-unknown-elf-gcc -o hello.elf -T link_tcm.ld hello.o sc_print.o crt_tcm.o ...

# 3. 转成 testbench 能加载的 .hex（objcopy -O verilog）
riscv64-unknown-elf-objcopy -O verilog hello.elf hello.hex

# 4. 顺便生成反汇编 dump
riscv64-unknown-elf-objdump -D hello.elf > hello.dump
hello.hex 里到底长什么样
.hex 就是纯文本的 16 进制指令流。CPU 复位后从地址 0 开始逐条取指执行。testbench 在仿真开始前把整个 .hex 读进模拟内存，相当于"烧录"了程序。

四、第 2 步：编译仿真器（Verilog → C++）

SCR1 的 RTL 是 Verilog/SystemVerilog，Verilator 把它翻译成 C++，再用 g++ 编译成可执行仿真器。这一步由 sim/Makefile 的 build_verilator 目标完成。

SRC 全部 .sv
（IFU/IDU/EXU/... + testbench）
→
Verilator
翻译成 C++
→
g++ 编译
+ 仿真 wrapper
→
Vscr1_top_tb_ahb
可执行仿真器

关键点：

  • 哪些 RTL 文件参与编译：顶层 Makefile 按 AHB 总线选 ahb_top.files，它列出 core + top + tb 的所有 .sv 文件（IFU/IDU/EXU/CSR/MPRF/LSU/IALU/IPIC/CLKCTRL + testbench）
  • --exe wrapper：sim/verilator_wrap/scr1_ahb_wrapper.c 提供 C 语言 main()，负责时钟循环、调用 testbench 的顶层模块
  • 快速版 vs 波形版：build_verilator 不带波形（快）；build_verilator_wf 带 VCD 波形（慢，学习迭代别用）
注意：这一步很耗时但只做一次
Verilator 编译整个 SCR1 需要几分钟，但它只在第一次或 RTL 改动后重新编译。只要没改 Verilog 代码，后续运行直接复用已编译好的仿真器（make 会检测文件时间戳）。

五、第 3 步：运行仿真（.hex 被 CPU 执行）

make 最后执行编译好的仿真器，把测试列表传给它：

# make 实际执行的命令（简化）
build/verilator_AHB_MAX_imc_IPIC_1_TCM_1_VIRQ_1_TRACE_0/verilator/Vscr1_top_tb_ahb \
    +test_info=.../test_info \
    +test_results=.../test_results.txt \
    +imem_pattern=FFFFFFFF \
    +dmem_pattern=FFFFFFFF

仿真器内部发生的事：

1 加载 .hex：scr1_top_tb_runtests.sv 读取 test_info 里的测试名（hello.hex），把指令写入模拟 IMEM
2 复位：testbench 拉低复位信号几个周期，然后释放，CPU 从复位向量地址 0x0 开始取指
3 逐周期执行：Verilator 在每个时钟边沿评估所有信号，模拟 IFU→IDU→EXU 流水线推进
4 检测退出：testbench 持续监视 PC，当 PC 到达 SCR1_SIM_EXIT_ADDR（测试的退出地址）时判定程序结束
5 判断 PASS/FAIL：testbench 检查退出时的返回值寄存器（a0），据此输出 PASS/FAIL

六、读懂仿真结果

运行结束后控制台输出三部分关键信息：

scr1_top_tb_ahb                                ← 仿真器顶层模块名

---Test:                        hello.hex       ← 正在运行哪个测试
Hello from SCR1!                                ← 程序自己的 printf 输出
Test passed                                     ← testbench 判定结果

#--------------------------------------
# Summary: 1/1 tests passed                    ← 汇总
#--------------------------------------

                    hello.hex		OK	  PASS    ← 汇总表
输出段含义
---Test: hello.hextestbench 开始加载并运行该测试
Hello from SCR1!程序通过串口打印输出到仿真控制台（来自 sc_printf）
Test passedtestbench 检查退出返回值正确
Summary: 1/1 tests passed所有测试的汇总
PASS 的判定依据
testbench 检测 PC 到达退出地址后，读取返回值寄存器。hello 的 main 返回 0，testbench 检查 a0 是否为预期值——是则 PASS，否则 FAIL。这也解释了为什么你的测试程序最后要 return 0。

七、产出的文件分别是什么

所有产物都在构建目录 build/verilator_AHB_MAX_imc_IPIC_1_TCM_1_VIRQ_1_TRACE_0/：

文件类型用途
test_info输入要运行的测试列表（每行一个 .hex）
test_results.txt输出每个测试的 PASS/FAIL 表
sim_results.txt输出仿真控制台完整日志（含 printf）
hello.elf中间产物ELF 可执行文件
hello.hex中间产物testbench 加载的指令文件
hello.dump中间产物反汇编清单（人看的，学习利器）
verilator/Vscr1_top_tb_ahb中间产物编译好的可执行仿真器

九、常见问题排查

问题 1：编译报 nano.specs 错误
症状：riscv64-unknown-elf-gcc: fatal error: cannot read spec file 'nano.specs'
原因：picolibc 环境不提供 nano.specs
解决：移除 sim/tests/common/common.mk 第 15 行的 --specs=nano.specs
问题 2：直接跑 make 命令报 weird 错误
症状：make 报 "mixed implicit and normal rules" 或 "No rule to make target"
原因：直接在命令行传了多个 make 目标（如 make clean_hex hello），顶层 Makefile 的 current_goal 计算会乱
解决：始终用 make TARGETS=<test> run_verilator 标准形式
问题 3：用了 run_verilator_wf 非常慢
症状：波形仿真跑了很久没结束，VCD 文件涨到 GB 级
原因：波形版把所有信号都写盘
解决：学习迭代一律用 run_verilator（无波形，秒级完成）；确需波形时再单独用 run_verilator_wf
一句话总结流程
make 一条命令 = 编译测试程序(.hex) + 编译仿真器 + 加载运行 + 自动判定结果。你只需要改代码，不需要碰任何仿真细节。
