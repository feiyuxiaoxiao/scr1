一、三种方式一句话

方式 A
跑现成测试 -- 零编写，验证环境
仓库自带 hello / isr_sample / riscv_isa 等测试，一条 make 命令跑完。
适合：刚开始，熟悉流程，确认环境正常。
方式 B
改现成程序 -- 改几行，验证概念
拿 hello.c 或 isr_sample.S 改几行，观察行为变化。
适合：学到某个概念（分支/中断/访存）后，动手验证。
方式 C
新建测试 -- 从零编写，理解最深
在 sim/tests/ 下建新目录，仿照 hello 模板写自己的程序。
适合：系统性地验证你对 SCR1 某个模块的理解。

三、方式 A：跑现成测试

仓库自带 4 类测试，命令都一样：

# 每个测试独立运行
make TARGETS=hello run_verilator        # 串口打印 "Hello from SCR1!"
make TARGETS=isr_sample run_verilator   # 三种中断：定时器/外部/软件
make TARGETS=riscv_isa run_verilator    # 几百条指令逐一验证（较慢）

# 也可以一次跑多个
make TARGETS="hello isr_sample" run_verilator
测试内容对应教程周次运行速度
hello打印字符串，验证基本执行第 6 周数据通路秒级
isr_sample三种中断 + CSR 断言第 4 周特权架构秒级
riscv_isaRV32I/M/C 指令逐一测试第 3 周 ISA较慢
riscv_compliance官方合规测试第 14 周验证慢
riscv_arch架构特权级测试第 4 周较慢
coremark / dhrystone性能基准第 14 周很慢
方式 A 的用法建议
方式 A 是最佳"冒烟测试"：每次你想确认"改过的代码/环境没坏"，跑一下 hello 即可。但它的学习价值有限——你只是看到 PASS/FAIL，不知道 CPU 内部发生了什么。要理解内部行为，需要用方式 B 配合 .dump 反汇编文件。

四、方式 B：改现成程序

方式 B 是"同一套骨架，改几行看变化"。这是最有性价比的学习方式。

两个可改的现成程序

hello.c（C 语言，最短）
// sim/tests/hello/hello.c 只有 6 行
#include "sc_print.h"

int main()
{
    sc_printf("Hello from SCR1!\n");
    return 0;
}
isr_sample.S（汇编，最长但最丰富）

291 行汇编，完整演示三种中断的触发、使能、处理、返回。配合第 4 周教程对照阅读效果最佳。

改法示例

// 例 1：改 hello.c -- 加一个循环，观察 printf 输出重复 3 次
int main()
{
    for (int i = 0; i < 3; i++)
        sc_printf("Hello from SCR1! %d\n", i);
    return 0;
}

// 例 2：改 isr_sample.S -- 把定时器到期值从 256 改成 1024
addi s1, s1, 256   →  addi s1, s1, 1024

// 或：删掉 csrs mie, a0 这一行使能，看测试是否 FAIL（验证"使能是必要条件"）
改完怎么运行？
和方式 A 完全一样！make TARGETS=hello run_verilator。make 检测到 .c 文件比 .hex 新，会自动重新编译，然后直接跑。你只需要观察输出的变化。
配合 .dump 反汇编理解内部行为
编译时自动生成 hello.dump，它把每条指令的地址、机器码、汇编一一列出。改程序后对比 dump，能直观看到"这行 C 代码被编译成了哪些 RISC-V 指令"。这是打通"C 语言层"和"CPU 硬件层"的最佳桥梁。

五、方式 C：新建测试

方式 C 是从零建一个测试目录。骨架照着 hello 抄即可，只需两步：

第 1 步：建目录和 Makefile

# 在 sim/tests/ 下新建目录，例如 my_prog
mkdir sim/tests/my_prog

# 创建 sim/tests/my_prog/Makefile（仿照 hello 的模板）
# 关键就 3 行：
src_dir := $(dir $(lastword $(MAKEFILE_LIST)))

c_src := sc_print.c my_prog.c            # 你写的 C 文件

include $(inc_dir)/common.mk           # 复用编译规则

第 2 步：写测试源码

// sim/tests/my_prog/my_prog.c
#include "sc_print.h"

int main()
{
    // 你想验证的逻辑写这里
    sc_printf("my test running\n");
    return 0;
}

第 3 步：运行

make TARGETS=my_prog run_verilator
想验证某个模块？可以从这几个点入手
  • 第 6 周：写一段数据依赖的指令序列，观察流水线停顿（配合 waveform 或 dump）
  • 第 4 周：复制 isr_sample 的框架，只保留定时器中断，加自己的处理逻辑
  • 第 10 周：写一个乘法循环，观察 IALU 的 MUL 多周期执行
  • 第 7 周：写带分支的代码，观察预测/冲刷行为
方式 C 的一个小坑
新测试目录必须在顶层 Makefile 里能识别。SCR1 的 Makefile 只对预设的测试名有规则（hello/isr_sample/riscv_isa...）。如果直接 make TARGETS=my_prog 会报 "No rule to make target"。解决：把 sim/tests/my_prog/Makefile 仿照 hello 那样，在顶层 Makefile 加一行规则（或在 tests 目标的依赖里加上 my_prog）。

阶段做什么建议动作对应教程
1. 方式 A跑通 hello + isr_sample看输出、看 dump，搞懂流程本页 + 方式 A 流程页
2. 方式 B改 hello.c 加循环/运算对比 dump，理解 C→指令映射第 6 周数据通路
3. 方式 B+改 isr_sample 中断逻辑删/加使能位，观察行为变化第 4 周特权架构
4. 方式 C写自己的最小测试验证流水线停顿、MUL 多周期等第 9-10 周
一句话建议
先 A 后 B 再 C。A 让你敢跑，B 让你看懂，C 让你会用。大部分学习时间应该花在 B 上——它是"改动最小、反馈最快、理解最深"的结合点。
