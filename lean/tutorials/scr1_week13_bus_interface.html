第三课: AHB-Lite 总线协议详解

AHB-Lite 是 ARM AMBA 3 协议族的简化子集
SCR1 使用 AHB-Lite 作为外部总线接口。与全功能 AHB 相比, AHB-Lite 去掉了 "split/retry" 响应多主设备仲裁和总线锁定, 仅保留单一主设备 + 多从设备架构。核心优势: 协议简单、面积小、延迟可预测。

AHB-Lite 信号表

信号名方向位宽说明
HCLK全局1总线时钟, 所有传输在此上升沿同步
HRESETn全局1总线复位 (低有效)
HADDRMaster→Slave32系统地址总线
HWRITEMaster→Slave1传输方向: 0=读, 1=写
HSIZEMaster→Slave3传输大小: 000=字节, 001=半字, 010=字
HBURSTMaster→Slave3突发类型: 000=SINGLE, 001=INCR, 其他=WRAP/INCR4/INCR8/INCR16
HTRANSMaster→Slave2传输类型: 00=IDLE, 01=BUSY, 10=NONSEQ, 11=SEQ
HPROTMaster→Slave4保护控制: [3]=Cacheable, [2]=Bufferable, [1]=Privileged, [0]=Data/Opcode
HWDATAMaster→Slave32写数据总线 (仅写事务)
HRDATASlave→Master32读数据总线 (仅读事务)
HREADYSlave→Master1传输完成标志: 1=当前传输完成, 0=插入等待
HRESPSlave→Master2传输响应: 00=OKAY, 01=ERROR

HTRANS 传输类型

HTRANS[1:0]类型说明
00IDLE主设备无数据传输请求。从设备必须忽略该传输并返回 OKAY + 零等待状态
01BUSY主设备正在执行突发, 但下一传输无法立即进行。从设备必须返回 OKAY + 零等待状态
10NONSEQ单个传输或突发的第一个传输。地址与控制信息与前一次传输无关
11SEQ突发中的剩余传输。地址 = 前一次传输地址 + (1<
SCR1 的 HTRANS 使用
SCR1 单发射顺序核始终使用 NONSEQ + SINGLE 模式, 每次只发起一个 32 位传输。不使用 INCR/WRAP 突发 — 这是 Harvard 架构 + 顺序执行的自然结果。HTRANS 在 IDLE 和 NONSEQ 之间切换。

错误响应: 读错误

T0 T1 T2 T3 T4 T5 HCLK _|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_ HADDR ----<A>------------------------------- HTRANS ----<NONSEQ>----------<IDLE>---------- HWRITE ----< 0 >------------------------------- HREADY --------<1>----<1>-------------------- HRDATA -----------------------------<XXXX>---- HRESP -------------<OKAY>------<ERROR>------- | | 地址+控制认可 两阶段错误响应 HRESP=OKAY 在 HREADY=1 时仅表示从设备已接受控制信息 真正的 ERROR 出现在数据阶段 HREADY=1 拍
AHB 两阶段错误响应机制
AHB-Lite 的 HRESP 需要两拍来完成错误上报: 第一拍 (地址阶段) 从设备必须返回 OKAY 以接收地址/控制信息; 第二拍 (数据阶段) 从设备返回 ERROR 表示访问失败。这不是协议缺陷, 而是流水线架构的必然 — 地址译码需要一拍。

错误响应: 写错误

T0 T1 T2 T3 T4 T5 HCLK _|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_ HADDR ----<A>------------------------------- HTRANS ----<NONSEQ>----------<IDLE>---------- HWRITE ----< 1 >------------------------------- HWDATA ----< W(A) >--------------------------- HREADY --------<1>----<1>-------------------- HRESP -------------<OKAY>------<ERROR>------- | | 控制信息确认 ERROR 上报 写 ERROR 意味着数据未写入, 主设备需要采取错误处理措施
HRESP 两拍的原因
地址拍: 从设备还未完成地址译码, 只能返回 OKAY 先接收控制信息。
数据拍: 从设备已完成译码并判定地址非法/设备故障, 返回 ERROR。
HREADY 控制整个流水线推进 — 若 HRESP=ERROR 且 HREADY=1, 主设备立即标记该事务失败。

Router 的关键约束: 单主设备 → 多从设备
一次请求只能路由到一个从设备。Router 是纯组合逻辑地址译码, 无状态, 不缓冲 — 所有握手和反压由下游从设备 (TCM / AHB) 各自处理。

第六课: Router 扩展 — 地址译码与优先级

DMEM Router 的完整路由表 (3 目标)

地址范围目标从设备说明
TCM_BASE ~ TCM_BASE+SIZE-1TCM (Port B)片内紧耦合 SRAM, 1 拍延迟
TIMER_BASE ~ TIMER_BASE+0x1FTimer内存映射定时器, 地址掩码 0xFFFFFE0
其余地址AHB 数据桥通过 AHB-Lite 访问外部存储/外设

地址译码组合逻辑

// IMEM Router 地址匹配 (2 目标)
assign imem_tcm_sel   = (imem_addr & TCM_MASK) == TCM_BASE;
assign imem_debug_sel = (imem_addr & DEBUG_MASK) == DEBUG_BASE;
assign imem_ahb_sel   = ~imem_tcm_sel & ~imem_debug_sel;

// DMEM Router 地址匹配 (3 目标: TCM / Timer / AHB)
assign dmem_tcm_sel   = (dmem_addr & TCM_MASK)   == TCM_BASE;
assign dmem_timer_sel = (dmem_addr & TIMER_MASK) == TIMER_BASE;
assign dmem_ahb_sel   = ~dmem_tcm_sel & ~dmem_timer_sel;

请求分发与应答汇聚 — 优先级

// 当 TCM 和 AHB 都能响应时需要优先级仲裁
// TCM 优先级最高 (紧耦合), Timer 次之, AHB 最低

assign dmem_resp_src = dmem_tcm_sel   ? TCM_RESP   :
                        dmem_timer_sel ? TIMER_RESP :
                                         AHB_RESP;

// req_ack 也需要按优先级合并:
assign lsu_req_ack = dmem_tcm_sel   ? tcm_req_ack   :
                      dmem_timer_sel ? timer_req_ack :
                                       ahb_req_ack;
Router 的纯组合逻辑特性
Router 不含任何寄存器。地址译码、请求分发、应答回传全部在同拍完成。这意味着: 哪个从设备被选中, 就完全由该从设备的 req_ack 决定主设备何时握手成功; Router 自身不引入任何额外延迟。所有从设备的 req_ack 通过 MUX 汇聚到主设备一侧。

TCM 的 0 延迟: 为什么
TCM 直连 dp_memory 的同步端口, 请求发出后 1 拍返回数据。相比通过 AHB 总线 (需要仲裁 + 多拍握手), TCM 消除了所有协议开销, 实现 1 拍吞吐。代价: TCM 容量受芯片面积限制 (通常 64KB-256KB)。

第八课: dp_memory — 双端口同步 RAM

// scr1_dp_memory.sv: 双端口 + 字节写使能
module scr1_dp_memory
    parameter SCR1_WIDTH = 32,      // 数据宽度
    parameter SCR1_SIZE  = ...        // 存储器大小 (字节)
(
    // Port A: 只读 (IMEM)
    input  rena, addra,
    output qa,
    // Port B: 读写 (DMEM), 带字节写使能
    input  renb, wenb, webb[3:0], addrb, datab,
    output qb
);

字节写使能 (webb) 的实现 (Intel FPGA)

wenbb = {4{wenb}} & webb;        // 4 个字节独立控制

always_ff @(posedge clk) begin
    if (wenb) begin
        if (wenbb[0]) memory_array[addrb][0] <= datab[ 0:7];
        if (wenbb[1]) memory_array[addrb][1] <= datab[ 8:15];
        if (wenbb[2]) memory_array[addrb][2] <= datab[16:23];
        if (wenbb[3]) memory_array[addrb][3] <= datab[24:31];
    end
    qb <= memory_array[addrb];
end
为什么需要字节写使能?
SB 指令只写 1 字节, SH 写 2 字节, SW 写 4 字节。RAM 必须按字节粒度控制, 否则 SB 会将整个 32 位字全部覆盖, 破坏相邻字节。webb[3:0] 由 LSU 根据 lsu_cmd 译码生成。

非 FPGA 实现 (ASIC / 仿真)

// 直接使用 32 位宽的 RAM block (无字节写使能)
// 由 synthesis 工具推断为 SRAM / register file
always_ff @(posedge clk) begin
    if (wenb) ram_block[addrb] <= datab;
    qb <= ram_block[addrb];
end
always_ff @(posedge clk)
    qa <= ram_block[addra];

第十课: SCR1 作为 AHB 主设备 — 仲裁层次

SCR1 有 2 个独立 AHB Master
scr1_imem_ahb — 指令 AHB 主设备, 仅发起读传输
scr1_dmem_ahb — 数据 AHB 主设备, 发起读/写传输
两个 Master 独立工作, 各自有独立的 AHB 总线信号。指令通道和数据通道不需要互斥仲裁, 因为它们是两条物理独立的 AHB-Lite 总线。

请求/响应分离流水线

// scr1_imem_ahb / scr1_dmem_ahb 的核心: FIFO 缓冲
// 请求打入 req_fifo → AHB Master FSM 逐条消费
// 响应由 AHB 总线返回 → resp_fifo → mem_if 协议

T0:  IFU 发出 req[0] → req_fifo.push(req[0])
     AHB_FSM: IDLE, 无请求待发

T1:  IFU 发出 req[1] → req_fifo.push(req[1])
     AHB_FSM: 从 req_fifo 取出 req[0], 驱动 HADDR, HTRANS=NONSEQ

T2:  IFU 不请求
     AHB_FSM: req[0] 地址阶段完成, HREADY=1 → 等数据
              取出 req[1], 驱动下一个地址

T3:  HRDATA[0] 返回 → resp_fifo.push(data[0])
     AHB_FSM: req[1] 等待

T4:  HRDATA[1] 返回 → resp_fifo.push(data[1])
     resp_fifo → imem2ifu_rdata (按序返回)
FIFO 的作用: 解耦请求速率与 AHB 总线延迟
当 AHB 总线因从设备忙而插入等待 (HREADY=0) 时, IFU/LSU 可以继续发出请求存入 FIFO (只要 FIFO 未满)。当总线空闲时, AHB Master FSM 从 FIFO 取请求快速发射。FIFO 将流水线停顿从 "全局阻塞" 降级为 "FIFO 满时阻塞"。

第十一课: AHB 从设备多路复用器

SCR1 SoC 的 AHB 互联架构
SCR1 使用地址译码 + 多路复用器方案连接多个 AHB 从设备。这是 AHB-Lite 单主设备系统的标准互联方式 — 无需总线仲裁, 所有从设备共享主设备的地址/控制总线, 通过地址译码选中唯一活跃从设备。

AHB 从设备选择逻辑

// 地址译码: 根据 HADDR 生成 HSELx
parameter TCM_BASE   = 32'h0000_0000;
parameter TCM_SIZE   = 32'h0001_0000; // 64KB
parameter TIMER_BASE = 32'h0049_0000;
parameter TIMER_SIZE = 32'h0000_0020; // 32B

assign HSEL_TCM   = (HADDR >= TCM_BASE)   & (HADDR < TCM_BASE + TCM_SIZE);
assign HSEL_TIMER = (HADDR >= TIMER_BASE) & (HADDR < TIMER_BASE + TIMER_SIZE);
assign HSEL_EXT   = ~HSEL_TCM & ~HSEL_TIMER;

// 响应 MUX: 未选中的从设备输出 0, 选中的驱动实际值
assign HRDATA = ({32{HSEL_TCM}}   & hrdata_tcm  )
                | ({32{HSEL_TIMER}} & hrdata_timer)
                | ({32{HSEL_EXT}}   & hrdata_ext  );

assign HRESP  = HSEL_TCM   ? hresp_tcm   :
                  HSEL_TIMER ? hresp_timer :
                               hresp_ext;

assign HREADY = HSEL_TCM   ? hready_tcm   :
                  HSEL_TIMER ? hready_timer :
                               hready_ext;
HREADY 多路复用的陷阱
AHB-Lite 中, 每个从设备都有自己的 HREADYout。多路复用器必须确保只有当前被 HSELx 选中的从设备的 HREADY 被传递给主设备。未选中的从设备应输出 HREADY=1 (以不阻塞总线), 但不直接连到 MUX 输入端 — 通常通过 AND-OR 结构: master_hready = (HSEL_TCM & hready_tcm) | (HSEL_TIMER & hready_timer) | (HSEL_EXT & hready_ext)。

LSU 中 HRESP=ERROR 的处理

// scr1_pipe_lsu.sv: DMEM ERROR 响应处理
assign dmem_resp_er = (dmem2lsu_resp_i == SCR1_MEM_RESP_RDY_ER);

// 异常代码选择 (优先级编码):
// LD_ACCESS_FAULT: 加载指令收到 HRESP=ERROR
// ST_ACCESS_FAULT: 存储指令收到 HRESP=ERROR
case (1'b1)
    dmem_resp_er & lsu_cmd_ff_load:  exc_code = SCR1_EXC_CODE_LD_ACCESS_FAULT;
    dmem_resp_er & lsu_cmd_ff_store: exc_code = SCR1_EXC_CODE_ST_ACCESS_FAULT;
    ...
endcase

// 异常优先级: DMEM ERROR > 断点 > 地址未对齐
// 这是因为: 一旦 DMEM 返回 ERROR, 数据已不可用,
// 其他异常 (未对齐/断点) 已经没有意义
AHB ERROR 的完整异常处理流程 (以 LW 为例)
1. LUI 发出 LW a0, 0(a1), 地址落在非法外部总线范围
2. DMEM Router 将请求路由到 dmem_ahb, AHB Master 驱动 HADDR
3. 外部 AHB 从设备检测地址非法, 在数据拍返回 HRESP=ERROR, HREADY=1
4. dmem_ahb 收到 ERROR → resp_fifo → 转换为 dmem_resp=RDY_ER
5. LSU 的 dmem_resp_er 置 1 → 产生 LD_ACCESS_FAULT 异常
6. EXU 仲裁: 将当前指令标记为异常, 保存 PC→MEPC, 异常码→MCAUSE, 地址→MTVAL
7. 流水线清空, 下一条 PC = MTVEC (异常入口地址)

IFU 取指错误的处理 (AHB 指令总线)

// 取指时 HRESP=ERROR → INSTR_ACCESS_FAULT
// IFU 的错误处理更为关键: 因为没有指令就无法执行

AHB Imem: HRESP=ERROR

第十五课: Timer 的 AHB 从设备接口

Timer 作为内存映射外设: AHB Slave 接口
Timer 在 SoC 中作为 AHB 从设备, 被 DMEM AHB Master 通过地址译码访问。Timer 内部实现 mem_if 或直接 AHB 从设备协议, 将 AHB 读/写转换为寄存器访问。

AHB Slave 接口实现 (简化)

// Timer 的 AHB 从设备接口: 处理 HTRANS + HADDR → 寄存器读写

always_ff @(posedge HCLK) begin
    if (HSEL & HTRANS[1] & HREADY) begin
        if (~HWRITE) begin  // 读
            case (HADDR[4:0])
                5'h00: hrdata <= mtime[31:0];
                5'h04: hrdata <= mtime[63:32];
                5'h08: hrdata <= mtimecmp[31:0];
                5'h0C: hrdata <= mtimecmp[63:32];
                5'h10: hrdata <= timer_ctrl;
                default: hrdata <= 0;
            endcase
        end else begin  // 写
            case (HADDR[4:0])
                5'h00: mtime[31:0]  <= HWDATA;
                5'h04: mtime[63:32] <= HWDATA;
                5'h08: mtimecmp[31:0]  <= HWDATA;
                5'h0C: mtimecmp[63:32] <= HWDATA;
                5'h10: timer_ctrl      <= HWDATA[11:0];
            endcase
        end
    end
end

assign HREADYout = 1'b1;  // Timer 零等待, 始终就绪
assign HRESPout  = 2'b00; // OKAY, Timer 自身不产生 ERROR

DM 访问与 CPU 访问的仲裁

// 当 DM 和 CPU 同时访问相同的 AHB 从设备时,
// 需要 AHB Bus Matrix 进行仲裁。
// SCR1 简化方案: DM 访问时暂停 CPU (hart halted)

always_comb begin
    if (dm_active) begin
        // DM 模式: CPU 暂停, DM 独占总线
        hmaster_sel = DM_MASTER;
    end else begin
        // 正常运行模式
        hmaster_sel = CPU_MASTER;
    end
end
SCR1 调试访问的实际仲裁策略
SCR1 采用 "暂停即切换" 策略: 当调试器通过 JTAG 发出 halt 请求, CPU 进入调试模式 (hart halted), 此时 HDU 接管控制权; DM 通过 AHB Master 口直接读写处理器资源。CPU 恢复运行后, DM 释放 AHB 总线。这种设计避免了复杂的多主设备仲裁器, 代价是调试期间 CPU 无法并发执行。
