第二课: ADD x5, x1, x2 -- 算术指令追踪

指令编码与译码

// ADD x5, x1, x2
// 编码: 0000000_00010_00001_000_00101_0110011
// funct7=0000000  rs2=x2  rs1=x1  funct3=000  rd=x5  opcode=OP

T0 PC=0x200
发 IMEM 请求		 空闲 空闲 —

T2 PC=0x204

译码：funct7=0, rs2=x2, rs1=x1, funct3=0, rd=x5, opcode=OP		 空闲 —
T3 PC=0x208 下一指令 执行：读 x1=5, x2=3

ADD 是最快指令
ADD 不访存、不跳转，纯寄存器操作。T3 周期同拍完成"读寄存器→ ALU 运算→写回"——这正是 SCR1 无数据冲突的根本原因：操作数获取（阶段 4）和写回（阶段 8）在同一个 EXU 周期完成。

跟踪中断时 MEPC 的优先级生效

如果 T3 周期同时有一个外部中断到来，csr2exu_irq_o 会拉高，EXU 内部走异常处理路径，此时 ADD 不会被提交，而是进入 trap。

第三课: LW x6, 4(x1) -- LOAD 指令追踪

假设 x1 = 0x1000，目标：从地址 0x1004 读 32 位数据到 x6。

周期IFUIDUEXU(LSU)MPRF
T0取指 0x200———
T1收指令———
T2取指 0x204译码：opcode=LOAD, funct3=010(LW), rs1=x1, rd=x6, imm=4——
T3取指 0x208下一指令发 DMEM 请求：
addr = x1+4 = 0x1004
cmd = LW		—
T4——等 DMEM 响应
LSU FSM = BUSY		—
T5——收 DMEM 数据
写 x6 = 0xDEADBEEF		x6 = 0xDEADBEEF
LOAD 的 2 周期 DMEM 延迟
LOAD 在 T3 发请求，T4 的 BUSY 状态等待（LSU 的 exu_rdy = lsu_rdy），T5 才拿到数据写回。这 2 个周期的 DMEM 响应时间是 TCM 的标准延迟（dmem_req_vd 到 dmem_resp_received）。

WEIGHT 吞吐量是 2 而非 1

虽然延迟是 5 周期（4 级流水线 + TCM IFU 延迟 + DMEM 响应），但 吞吐量是 2：因为写回和取指并行，且没有结构冲突。连续两条 LOAD 可以在 T3 和 T5 分别发请求。

第四课: SW x2, 8(x1) -- STORE 指令追踪

假设 x1 = 0x1000, x2 = 0xABCD，目标：把 0xABCD 写入地址 0x1008。

周期IFUIDUEXU(LSU)
T0取指 0x200——
T1收指令——
T2取指 0x204译码：opcode=STORE, funct3=010(SW), rs1=x1, rs2=x2, imm=8(S-type)—
T3取指 0x208下一指令发 DMEM 写请求：
addr = 0x1008, wdata = 0xABCD, cmd = SW
T4——等 DMEM 响应（BUSY）
T5——DMEM 写完成
指令退休
STORE vs LOAD 的关键差异
STORE 不需要写回 MPRF（它不修改寄存器）。T5 只确认 DMEM 写完成，然后 exu2pipe_instret_o 拉高标记指令退休。STORE 的 exu2mprf_w_req 始终为 0。

STORE 地址未对齐异常

// LSU 中的对齐检查
assign lsu_addr_misaligned = (exu2lsu_cmd_i == SCR1_LSU_CMD_SW) & exu2lsu_addr_i[1:0] != 2'b00
                            | (exu2lsu_cmd_i == SCR1_LSU_CMD_SH) & exu2lsu_addr_i[0]   != 1'b0;

STORE 的地址必须在字边界对齐（SW）或半字边界对齐（SH）。SB 无对齐要求。

第五课: BEQ x1, x2, label -- 分支指令追踪

假设 x1 = x2 = 5, label 偏移 = -8 (即跳转到 PC-8)。BEQ 是条件分支，只有条件满足时才跳转。

周期IFUIDUEXU
T0取指 0x200——
T1收指令——
T2取指 0x204译码：opcode=BRANCH, funct3=000(BEQ), rs1=x1, rs2=x2, imm=B-type—
T3取指 0x208（推测顺序执行）下一指令 IALU 做减法比较：
x1-x2=0 → z=1
跳转已采用
new_pc = 0x200 + (-8) = 0x1F8
new_pc_req = 1
T4 清空队列
0x208 的指令被丢弃
重新取指 0x1F8		 0x208 被清空空闲
T5收 0x1F8 指令——
分支的资源浪费
T3 时 IFU 已经"乐观"取了 0x208 的指令（因为它不知道分支会不会跳转）。T3 发现 BEQ 条件满足后，T4 必须清空流水线（flush）——0x204 和 0x208 的指令全部废弃。这是顺序处理器无分支预测的固有代价。

EXU 端的 PC 多路器再次回顾

BEQ 触发 jb_taken 信号，对应优先级 6（最低），因为新 PC 值走 ialu_addr_res & SCR1_JUMP_MASK 计算。

// scr1_pipe_exu.sv -- new PC 请求条件
exu2ifu_pc_new_req_o = ...
    | (exu_queue_vd & jb_taken)      // 分支/跳转采用

第六课: JAL x1, label -- 无条件跳转追踪

JAL (Jump And Link) 做两件事：把返回地址（PC+4）写入 rd，然后无条件跳转到目标地址。

周期IFUIDUEXUMPRF
T0取指 0x200———
T1收指令———
T2取指 0x204译码：opcode=JAL, rd=x1, imm=J-type
jump_req=1, rd_wb_sel=INC_PC
sum2_op=PC_IMM		——
T3取指 0x208下一指令 地址加法器：PC+imm = 目标地址
INC_PC：0x200+4 = 0x204
new_pc = 目标地址
写 x1 = 0x204		 x1 = 0x204
rd_wb_sel=INC_PC 的来源
JAL 写回的 不是 ALU 结果，而是 PC + 4。IDU 在译码时就指定 rd_wb_sel = INC_PC，EXU 内部有专门的 inc_pc = curr_pc + 4（RVC 时 +2）通路直接将此值路由到 MPRF 写端口。

第七课: CSRRW x3, MSTATUS, x4 -- CSR 读写追踪

CSR 指令需要走 EXU→CSR→EXU 的往返路径。

周期IFUIDUEXU→CSR（同周期）MPRF
T2—译码：opcode=SYSTEM, funct3=001(CSRRW), rs1=x4, rd=x3, csr_addr=0x300
csr_cmd=WRITE, csr_op=REG		——
T3—— EXU 发 CSR 写请求：
exu2csr_rw_addr = 0x300
exu2csr_w_data = x4 的值
exu2csr_w_cmd = WRITE

CSR 返回旧值：
csr2exu_r_data = 旧 MSTATUS
写 x3 = 旧 MSTATUS		 x3 = 旧 MSTATUS 
// CSRRW 的时序要点
// T3 同周期完成：EXU → CSR(写) → EXU(读旧值) → MPRF(写回)
// 写 MSTATUS 后的额外延迟：
csr2exu_mstatus_mie_up_o = 1'b1;  // 标记 mstatus 已更新
exu_rdy = 1'b0;                // EXU 停止提交一周期
CSR 写 MSTATUS/MIE 需额外一周期
当写入的 CSR 是 MSTATUS 或 MIE 时，EXU 会额外暂停一个周期（csr2exu_mstatus_mie_up_o 拉高），确保新的 MIE 值在下一周期才生效。这个周期 exu_rdy = 0，不允许任何指令提交。

延迟计算公式
延迟 = 流水线级数 + (TCM 取指额外延迟) + (DMEM 响应延迟) + (flush 惩罚)。其中流水线级数包含 IFU 到 IDU 到 EXU 的寄存器路径，flush 惩罚为跳转后流水线清空一拍的代价。

第九课: 反压机制详解

SCR1 使用 就绪/有效握手协议 实现模块间反压：上游发 req，下游回 rdy，仅当两者同时有效时才传输数据。

关键反压链路

链路段请求信号就绪信号反压原因
IDU → IFUifu2idu_vdidu2ifu_rdyIDU 正在处理前一条指令或 EXU 忙
EXU → IDUidu2exu_reqexu2idu_rdyEXU 在执行多周期指令、LSU 忙、或 mstatus 更新中
// scr1_pipe_exu.sv -- EXU 就绪条件
always_comb begin
    case (1'b1)
        lsu_req                  : exu_rdy = lsu_rdy | lsu_exc_req;
        ialu_vd                  : exu_rdy = ialu_rdy;           // MDU 多周期
        csr2exu_mstatus_mie_up_i : exu_rdy = 1'b0;               // mstatus 更新
        default                  : exu_rdy = 1'b1;               // 默认就绪
    endcase
end
反压的级联传播
当 EXU 因为 LSU 忙而 exu_rdy=0 时，exu2idu_rdy=0 → IDU 停发新命令 → idu2ifu_rdy=0 → IFU 停止取指。整个流水线从后往前逐级传递反压信号。

IFU 队列的清空逻辑

// scr1_pipe_ifu.sv -- 队列清空
q_flush_req = exu2ifu_pc_new_req_i | pipe2ifu_stop_fetch_i;

always_ff @(posedge clk, negedge rst_n) begin
    if (~rst_n) begin
        q_rptr <= '0;
        q_wptr <= '0;
    end else if (q_flush_req) begin
        q_rptr <= '0;
        q_wptr <= '0;

end

IMEM 响应丢弃计数器

IFU 发出请求后，IMEM 的响应可能延迟多拍返回。PC 跳转时，这些"在途"的响应对应的指令已过时。IFU 用一个 imem_resp_discard_cnt 计数器忽略它们：
