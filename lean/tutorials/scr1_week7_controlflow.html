第一课: 本周概述

本周内容
正常程序流中 PC 按顺序递增 (+4 或 +2)。以下事件会改变程序流: JAL/JALR 跳转、BEQ/BNE 等分支、ECALL/MRET 陷阱、异常、中断、WFI 等待、调试暂停、复位。本周深入理解每种事件的 PC 生成机制、流水线暂停/清空、以及它们之间的优先级仲裁。

每条 NEW_PC 来源的详细信号路径

P1 init_pc -- 上电复位向量 
// scr1_pipe_exu.sv:664-674
// 4 位移位寄存器: init_pc_v[3:0] 复位时为 4'b0000
// 每个周期左移 1: 0000 → 0001 → 0011 → 0111 → 1111
if (~&init_pc_v) init_pc_v <= {init_pc_v[2:0], 1'b1};
assign init_pc = ~init_pc_v[3] & init_pc_v[2];  // 第 4 个周期: 0011 → 0111 时 init_pc=1
init_pc 仅在复位后的第 4 个 clk 上升沿有效 (单周期脉冲)。这是因为 CSR 需要几个周期来完成初始化。输出 SCR1_RST_VECTOR (默认为 0x200)。
P2 陷阱 (异常/中断/MRET) -- CSR 提供新 PC 
// scr1_pipe_exu.sv:707-712
case (1'b1)
    exu2csr_take_exc_o,    // 来自异常逻辑: exu_exc_req & ~hdu2exu_dbg_halted_i
    exu2csr_take_irq_o,    // 来自中断逻辑: csr2exu_irq_i & ~exu2pipe_exu_busy_o & ...
    exu2csr_mret_instr_o  :// 来自 MRET: exu_queue_vd & exu_queue.mret_req & ...
    exu2ifu_pc_new_o = csr2exu_new_pc_i;  // 该值来自 CSR 模块
csr2exu_new_pc_i 在 CSR 内部由事件类型决定: 异常取 MTVEC.BASE，中断取 MTVEC.BASE (Direct) 或 MTVEC.BASE + 4*cause (Vectored)，MRET 取 MEPC。
P3 调试恢复 -- HDU 提供 
// scr1_pipe_exu.sv:303
assign dbg_run_start_npbuf = hdu2exu_dbg_run_start_i & ~hdu2exu_pbuf_fetch_i;
仅在调试使能 (SCR1_DBG_EN) 时存在。排除 Program Buffer 取指场景，使用 HDU 提供的恢复 PC。
P4 WFI 退出 -- PC 保持不变 
// scr1_pipe_exu.sv:716
wfi_run_start_ff    : exu2ifu_pc_new_o = pc_curr_ff;  // WFI 后继续执行下一条
wfi_run_start_ff 指示 HART 刚从中断等待状态恢复。新 PC 设为当前 PC (pc_curr_ff)，即 WFI 下一条指令的地址。
P5 FENCE.I -- 指令缓存同步 
// scr1_pipe_exu.sv:717
exu_queue.fencei_req : exu2ifu_pc_new_o = inc_pc;  // inc_pc = pc_curr_ff + 2(AVG)/4
FENCE.I 策略是继续执行下一条指令，同时通知 IFU 冲刷队列以确保 I/D 一致性。
P6 默认 -- 跳转/分支地址 
// scr1_pipe_exu.sv:718
default : exu2ifu_pc_new_o = ialu_addr_res & SCR1_JUMP_MASK;
// SCR1_JUMP_MASK = 32'hFFFF_FFFE: 清除 bit[0] 保证半字对齐
// ialu_addr_res 来自于地址加法器 SUM2 的输出
当 jb_taken = exu_queue.jump_req | branch_taken 时，使用地址加法器的计算结果。JAL + BRANCH 使用 pc_curr_ff + imm，JALR 使用 rs1 + imm。

NEW_PC 请求信号 (exu2ifu_pc_new_req_o) 完整展开

// scr1_pipe_exu.sv:722-735 -- 每一行代表一个触发源
assign exu2ifu_pc_new_req_o =
    init_pc                                        // [1] 复位后第 4 周期
  | exu2csr_take_irq_o                             // [2] 中断被受理: csr2exu_irq_i & ~exu_busy & allowed
  | exu2csr_take_exc_o                             // [3] 异常被受理: exu_exc_req & ~dbg_halted
  | (exu2csr_mret_instr_o & ~csr2exu_mstatus_mie_up_i)   // [4] MRET (等 MSTATUS 更新完)
  | (exu_queue_vd & exu_queue.fencei_req)               // [5] FENCE.I
  | (wfi_run_start_ff & clk_pipe_en)                    // [6] WFI 恢复
  | dbg_run_start_npbuf                                // [7] 调试恢复 (仅 SCR1_DBG_EN)
  | (exu_queue_vd & jb_taken);                         // [8] 跳转/分支采用
MRET 的 MSTATUS 同步问题
MRET 的 new_pc_req 条件中多了 & ~csr2exu_mstatus_mie_up_i。这是因为 MRET 需要先更新 MSTATUS (MIE←MPIE, MPIE←1)，如果 MSTATUS 同周期也在更新 (mie_up=1)，则延迟一个周期发送 new_pc_req。这导致了 MRET 的额外 1 周期延迟。
为什么 P2 中三个信号共享一个分支？
exu2csr_take_exc_o、exu2csr_take_irq_o、exu2csr_mret_instr_o 三者不会同时为 1，因为: (1) 异常和中断由硬件互斥；(2) MRET 和异常/中断不可能在同周期产生异常 (MRET 不触发异常，它只更新 CSR)。但 case(1'b1) 的语法确保了任意情况下只有一个生效。

always_comb begin
    if (exu_queue.sum2_op == SCR1_SUM2_OP_REG_IMM) begin

JALR 的地址对齐
JALR 在 RISC-V 规范中要求目标地址最低位清零 (& ~1)。在 SCR1 中通过 ialu_addr_res & SCR1_JUMP_MASK 实现，SCR1_JUMP_MASK 在有 RVC 时为 32'hFFFF_FFFE (清除 bit[0])，无 RVC 时清除 bit[1:0]。

第四课: 分支预测与判定的完整时序

SCR1 的分支预测策略: 静态预测不跳转 (Static Predict-Not-Taken)

SCR1 实现的是最朴素的分支预测: 总是假设分支不跳转。当分支条件在 EXU 阶段被评估为"条件成立 (taken)"时，IFU 已经按照"不跳转"的假设取回了错误路径上的指令。此时需要:

  1. Flush IFU 指令队列: 丢弃已取指但未执行的错误路径指令
  2. 从新 PC 地址重新取指: IFU FSM 转到 IDLE，然后重新发 FETCH

分支未采用 (Not Taken) 与采用 (Taken) 的完整时序对比

周期未采用 (Not Taken) -- 无惩罚采用 (Taken) -- 1 周期惩罚
T0 IFU 顺序取 0x200 (beq x1,x2,0x20) IFU 顺序取 0x200 (beq x1,x2,0x20)
T1 IFU 取 0x204 (beq 下一条), IDU 译码 0x200 IFU 取 0x204 (beq 下一条), IDU 译码 0x200
T2 IFU 取 0x208, IDU 译码 0x204, EXU 空 IFU 取 0x208, IDU 译码 0x204, EXU 空
T3 EXU 执行 beq: ialu_cmp=0 (条件不成立) jb_taken=0, 无 new_pc_req EXU 执行 beq: ialu_cmp=1 jb_taken=1 → new_pc_req=1, q_flush_req=1
T4 IDU 译码 0x208, EXU 执行 0x204 一切正常继续 IFU 队列清空 (rptr=wptr=0), ifu2idu_vd=0 IDU 收到无效数据, EXU 空闲
T5 继续流水 --- IFU FSM IDLE → FETCH: 从新地址 (0x220) 取指 IDU/EXU 空闲
T6 继续流水 --- IMEM 返回新指令, IDU 译码新指令 Bubble 结束

Flush 的 IFU 内部时序 -- 从 q_flush_req 到 q_is_empty

// scr1_pipe_ifu.sv:381, 388-395
assign q_flush_req = exu2ifu_pc_new_req_i | pipe2ifu_stop_fetch_i;

// 写指针复位: q_wptr <= 0 (下一个上升沿)
assign q_wptr_next = q_flush_req ? '0
                   : ~q_wr_none  ? q_wptr + (q_wr_full ? 'b010 : 'b001) : q_wptr;

// 读指针复位: q_rptr <= 0 (下一个上升沿)
assign q_rptr_next = q_flush_req ? '0
                   : ~q_rd_none  ? q_rptr + (q_rd_hword ? 'b001 : 'b010) : q_rptr;

// 队列空判断: q_is_empty = (q_rptr == q_wptr)

// scratch_pipe_ifu.sv:465
assign ifu_fetch_req = exu2ifu_pc_new_req_i & ~pipe2ifu_stop_fetch_i;

关键: q_flush_req=1 时，下一时钟周期 q_rptr=q_wptr=0，队列瞬间变"空"。同时 ifu_fetch_req=1 触发 IFU FSM 从 IDLE 转到 FETCH，开始从新 PC 取指。

为什么 Taken 分支有 1 周期 Bubble 惩罚？
因为 T3 才确定分支要跳转，IFU 在 T0-T2 已取回 0x204 和 0x208 两条错误指令。T3 发出 flush 后，T4 队列被清空，IDU 无指令可译码，EXU 无指令可执行 = Bubble。T5 才能重新取指。这 1 个周期也称为 分支误预测惩罚。

分支判定三步走

1 地址加法器 计算跳转目标: addr_res = pc_curr + imm(B-type)，使用 SCR1_SUM2_OP_PC_IMM
2 主 ALU 做比较: rs1 vs rs2，通过减法得出标志位 z, s, o, c
3 EXU 判定: branch_taken = exu_queue.branch_req & ialu_cmp，然后 jb_taken = jump_req | branch_taken 
// scr1_pipe_exu.sv:738-740
assign branch_taken = exu_queue.branch_req & ialu_cmp;
assign jb_taken     = exu_queue.jump_req | branch_taken;
assign jb_new_pc    = ialu_addr_res & SCR1_JUMP_MASK;

// 各种分支的 ialu_cmp 判定
// CMD_SUB_EQ:  z == 1   → BEQ  : 相等时跳转
// CMD_SUB_NE:  z == 0   → BNE  : 不等时跳转
// CMD_SUB_LT:  s ^ o    → BLT  : 有符号小于
// CMD_SUB_GE:  ~(s ^ o) → BGE  : 有符号大于等于
// CMD_SUB_LTU: ~c       → BLTU : 无符号小于
// CMD_SUB_GEU: c        → BGEU : 无符号大于等于

EXU Ready 判断: 谁决定 exu_rdy？

always_comb begin
    case (1'b1)
        lsu_req                 : exu_rdy = lsu_rdy | lsu_exc_req;  // LSU 忙时等待

MRET 的 2 周期延迟场景分析
正常情况 (无 MSTATUS 冲突): T3 MRET 提交 → T3 CSR 处理 → T3 pc_new_req → T4 IFU flush → T5 新取指。总计: 5 周期 (4 级流水 + 1 额外)。 MSTATUS 冲突情况: T3 MRET 提交但 csr2exu_mstatus_mie_up_i=1 → T3 csr_access_next=RDI, csr_access_init=0, mret_update=0 → T4 csr_access_ff=RDI, csr_access_init=1, mret_update=1 (MRET 生效) → T4 pc_new_req → T5 flush → T6 新取指。总计: 6 周期。

第九课续: 中断与异常的交互

中断受理条件: 严格的准入控制

// scr1_pipe_exu.sv:973-981
assign exu2csr_take_irq_o = csr2exu_irq_i           // CSR 模块发出中断请求

`ifdef SCR1_DBG_EN
                          & ~hdu2exu_irq_dsbl_i      // 中断未被调试器禁用
                          & ~hdu2exu_dbg_halted_i    // 不在调试暂停状态
`endif
`ifdef SCR1_CLKCTRL_EN
                          & clk_pipe_en              // 流水线时钟使能
`endif

为什么需要 ~exu2pipe_exu_busy_o？
exu2pipe_exu_busy_o = exu_queue_vd & ~exu_rdy。如果 EXU 正在等 LSU 完成或 MUL/DIV 完成，此时取中断会: (1) 无法正确保存当前指令的 PC 到 MEPC; (2) 导致复杂的数据一致性问题。因此 SCR1 简单地在 busy 期间屏蔽中断。

异常与中断的优先级关系: 同周期竞争裁决

场景同周期的异常同周期的中断实际响应逻辑
1 有异常 (exu_exc_req=1) 无中断 进入异常陷阱 take_exc 生效, take_irq=0
2 无异常 有中断 (csr2exu_irq_i=1) 进入中断陷阱 take_irq 生效如果 busy=0
3 有异常 (来自当前指令) 有中断 (外部异步) 进入异常陷阱 (异常优先) take_exc=1 时 busy=0，但 take_irq 的 csr2exu_irq_i 被 CSR 设为 0 直到异常提交完成
4 EXU busy (等待 LSU) 有中断 中断排队等待 take_irq 被 ~exu2pipe_exu_busy_o屏蔽

SCR1 的中断嵌套与委托

M 模式下的简单中断模型
SCR1 仅支持 M 模式 (Machine Mode)，因此没有中断委托 (delegation) 的概念。所有中断和异常都由 M 模式处理。进入陷阱时 MIE 清 0，因此默认情况下不支持中断嵌套。如果需要嵌套，陷阱处理程序必须:
  1. 在进入后尽快保存 MEPC 到栈
  2. 通过 CSRRW / CSRRS 将 MIE 置 1
  3. 在处理完毕 MRET 前恢复 MEPC
