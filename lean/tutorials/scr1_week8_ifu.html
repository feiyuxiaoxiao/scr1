3 种状态转移场景详解

场景触发条件转移方向作用
(A) 开始取指EXU 发出新 PC 请求 (跳转、分支、中断等) + 流水线未停止IDLE → FETCH启动取指流程
(B) 流水线暂停pipe2ifu_stop_fetch_i 拉高 (Stall / Flush / 调试暂停)FETCH → IDLE停止取指, 同时触发队列清空
(C) IMEM 错误未消化IMEM 返回错误 (resp=RDR_ER) 且丢弃计数器未归零 + 无新 PC 请求FETCH → IDLE等待丢弃计数器消化完所有错误后的在途响应
停止取指 ≠ 复位
pipe2ifu_stop_fetch_i 是来自流水线顶层的信号,在 Stall/Flush/调试暂停时拉高。IFU 回到 IDLE 后,队列也被清空 (q_flush_req=1),但已发出的 IMEM 请求不会收回 -- 靠丢弃计数器处理。

条件公式示例
判空q_rptr == q_wptrwptr=2, rptr=2 → 空
占用度 (半字)q_wptr - q_rptrwptr=5, rptr=2 → 占用 3 个半字
剩余半字空间 (下拍)4 - (q_wptr - q_rptr_next)保守: 假设读发生后的最坏情况
剩余字空间 (下拍)free_h_next >> 1半字转字, 用于与"有效在途"比较
可发新请求?free_w_next > imem_vd_pnd_txns_cnt保证在途响应都有位置写入队列
3 位指针 = 2 位地址 + 1 位圈数

例如指针值 3'b101: 圈数位 = 1, 地址位 = 2'b01, 表示第 2 圈的 slot 1。环形写指针超前读指针时, 差值自带圈数信息, 不用额外标志位。

q_has_free_slots 为什么用 q_rptr_next 而非 q_rptr? 如果当前周期 IDU 在读取队列, 队列空间会增加。设计者选择保守策略 -- 用 q_rptr_next (假设读操作不发生) 做空间估计, 确保在最坏情况下也不会因过度乐观而导致队列溢出。

WR_HI 的物理意义
PC 未对齐时 (addr[1]=1), 从字的高 16 位开始取指。此时低 16 位是无效指令 (属于上一条), 只有高 16 位有效。WR_HI 只存入高半, 跳过废数据。

第六课: RVC 检测逻辑 -- instr[1:0] 是关键

RISC-V 规范: 最低两位区分指令长度

instr[1:0]含义指令长度
2'b0016 位压缩指令 (Quadrant 0)16-bit (RVC)
2'b0116 位压缩指令 (Quadrant 1)16-bit (RVC)
2'b1016 位压缩指令 (Quadrant 2)16-bit (RVC)
2'b1132 位标准指令32-bit (RVI)
RISC-V 规范规定: 只要 instr[1:0] != 2'b11, 就是 16 位压缩指令。只有 instr[1:0] == 2'b11 是 32 位指令。

IFU 中的检测实现 (scr1_pipe_ifu.sv:279-280)

// 取出 IMEM 32 位数据的对应 [1:0] 位://   高 16 位的 [1:0] 对应 imem2ifu_rdata_i[17:16]
//   低 16 位的 [1:0] 对应 imem2ifu_rdata_i[1:0]

assign instr_hi_is_rvi = &imem2ifu_rdata_i[17:16];  // 高 16 位 [1:0] == 11 ? RVI
assign instr_lo_is_rvi = &imem2ifu_rdata_i[ 1: 0];  // 低 16 位 [1:0] == 11 ? RVI
IMEM 返回的 32 位字 ┌─────────────────────┬─────────────────────┐ │ bits[31:16] │ bits[15:0] │ │ 高 16 位 (上半字) │ 低 16 位 (下半字) │ │ ▲ │ ▲ │ │ [17:16] = [1:0] │ [1:0] = [1:0] │ │ instr_hi_is_rvi │ instr_lo_is_rvi │ │ = &[17:16] │ = &[1:0] │ └─────────────────────┴─────────────────────┘ 示例: 若 data[17:16] = 2'b11 → instr_hi_is_rvi = 1 → 高半是 RVI 若 data[17:16] = 2'b00 → instr_hi_is_rvi = 0 → 高半是 RVC

队列队首的类型判断 (scr1_pipe_ifu.sv:457-458)

// 从队列队首读出数据后, 同样通过 [1:0] 判断:
assign q_head_is_rvi    = &(q_data_head[1:0]);  // 队首 [1:0] == 11 ? RVI
assign q_head_is_rvc    = ~q_head_is_rvi;           // 否则就是 RVC (互补关系)
注意: 这是推测性判定
q_head_is_rvc 覆盖了 instr[1:0] = 00/01/10 三种情况, 全部判定为 RVC。对于合法的 RISC-V 代码, 这一判定总是正确的。但硬件本身不做深度校验 -- 它只检查 [1:0] 最低两位, 而不管这 16 位是否真的是合法的 RVC 编码。

00—1RVI_HI_RVI_LO低半是 RVI 高半, 高半是 RVI 低半
RVI_HI_RVI_LO: 为什么高半在前?
当取指地址 addr[1:0] = 00 且低 16 位是 RVI ([1:0]=11) 时, 指令的数据排布是 { 高 16 位, 低 16 位 }, 即高半 (bits[31:16]) 在低地址。硬件按地址递增顺序接收数据, 所以先收到高半、后收到低半。输出时需要调换为 { 低 16 位, 高 16 位 } 才是标准指令。

        if (exu2ifu_pc_new_req_i) begin              // 新 PC: 跨边界状态作废, 清零
            instr_hi_rvi_lo_ff <= 1'b0;
        end else if (imem_resp_vd) begin            // 有效响应: 更新跨边界状态
            instr_hi_rvi_lo_ff <= instr_hi_rvi_lo_next;
        end
    end
end

// 置位条件 (三种情况) (scr1_pipe_ifu.sv:320-322)
assign instr_hi_rvi_lo_next = (instr_type == SCR1_IFU_INSTR_RVI_LO_NV)
                             | (instr_type == SCR1_IFU_INSTR_RVI_LO_RVI_HI)
                             | (instr_type == SCR1_IFU_INSTR_RVI_LO_RVC);

三种置位条件的含义

instr_type场景为什么置 1?
RVI_LO_NV未对齐 PC, 高半 = RVI 低半高半部分是 RVI 的低 16 位, 等待下一轮 IMEM 返回高半来拼接
RVI_LO_RVI_HI对齐: 低半=RVI 低半, 高半=RVI 高半本轮 IMEM 的 RVI_LO 已经占用了低 16 位, 和 RVI_HI 不同条; 如果下一条是 RVI 且跨边界, 本轮的高半(RVI_HI) 可能成为下一条 RVI 的低半
RVI_LO_RVC对齐: 低半=RVI 低半, 高半=RVC高半是 RVC, 但低半的 RVI_LO 已经确认需要拼接; 下一轮如果高半=RVI_LO, 则说明出现了新的 RVI 跨边界
为什么只有 RVI 跨边界?
RVC 只有 16 位, 不会跨 32 位字边界。只有 32 位 RVI 指令可能被 32 位存储字切开: 前半个 RVI (低 16 位) 在字 N 的高 16 位, 后半个 (高 16 位) 在字 N+1 的低 16 位。

第十课: IMEM 握手协议时序波形详解

正常请求 → 响应流程

周期 T0 T1 T2 T3 T4 T5 CLK ▁/▔▔\▁/▔▔\▁/▔▔\▁/▔▔\▁/▔▔\▁/▔▔\ ifu_req ────▔▔▔▔▔▔▔▔▔▔▔▔▔────────────── imem_ack ────────────▔▔▔▔▔──────────────── handshake ────────────▔▔▔▔▔──────────────── (req & ack) pnd_cnt 0────1────1────2────1────0── imem_resp 00──00──00──01──00──00── (01 = RDR_OK) imem_rdata ─────────────INSTR0────────────── q_wr_en ─────────────▔▔▔▔▔────────────────
1 T0: IFU 拉高 req_o → 开始等待 IMEM 确认
2 T1: IMEM 拉高 ack_i → handshake_done=1, pnd_cnt+1 (req 已受理, 等待响应)
3 T2: IMF 可能继续发新请求 → pnd_cnt 继续累加
4 T3: IMEM 返回 resp=RDR_OK + 数据 → pnd_cnt-1, q_wr_en=1, 数据写入队列

背靠背 (Back-to-back) 请求: 流水线化

周期 T0 T1 T2 T3 T4 T5 T6 ifu_req ────▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔ imem_ack ────▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔ handshake ────▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔ pnd_cnt 0──1──2──3──2──1──0── imem_resp 00──00──00──01──01──01──00── (连续 3 个响应) imem_rdata ─────────────W0──W1──W2────── (每个数据隔 1 拍到达)
握手协议关键特征
  • 请求侧: IFU 拉高 ifu2imem_req_o, IMEM 用 imem2ifu_req_ack_i 确认。握手完成后, IFU 可以取消 req 或保持 req 发下一个请求。
  • 响应侧: IMEM 用 imem2ifu_resp_i 指示状态 (NOTRDY/RDY_OK/RDY_ER)。只有 RDY_OK 或 RDY_ER 时, imem2ifu_rdata_i 才有效。
  • 乱序支持: 在途计数器 (max=7) 允许发出多个请求后才收到第一个响应 -- 这是流水线化的基础。
  • 错误传播: resp=RDR_ER 时, 数据仍写入队列 (带 err=1), 触发丢弃计数器, 整个后续响应被丢弃。

第十一课: 丢弃计数器 -- 不看他、不用他、不理他

为什么需要丢弃?

PC 跳转后, 之前发出的 IMEM 请求还在回来的路上 (在途)。这些"过期"的响应不能进入队列 -- 它们是旧 PC 流的指令。最简单的方案: 数一数有多少个在途, 然后跳过这么多响应。

丢弃计数器的 3 个入口与寄存器 (scr1_pipe_ifu.sv:569-591)

// 更新条件: PC 跳转 / IMEM 错误 / 收到一个被丢弃的响应
assign imem_resp_discard_cnt_upd = exu2ifu_pc_new_req_i                    // 入口1: PC 跳转
                                  | imem_resp_er                            // 入口2: IMEM 错误
                                  | (imem_resp_ok & imem_resp_discard_req);  // 入口3: 丢弃成功 (计数-1)

// 计数器寄存器
always_ff @(posedge clk, negedge rst_n) begin
    if (~rst_n) begin imem_resp_discard_cnt <= '0; end
    else if (imem_resp_discard_cnt_upd) begin
        imem_resp_discard_cnt <= imem_resp_discard_cnt_next;
    end
end

// 次态: 无 NEW_PC_REG 版本

    exu2ifu_pc_new_req_i     ? imem_pnd_txns_cnt_next - imem_handshake_done   // PC 跳转: 在途总数 - 同拍握手补偿
  : imem_resp_er_discard_pnd ? imem_pnd_txns_cnt_next                         // IMEM 错误: 丢弃全部在途
                             : imem_resp_discard_cnt - 1'b1;                // 收到一个响应: 计数 -1

PC 跳转丢弃示例 (在途=5, 同拍有 1 次握手)

跳转前: imem_pnd_txns_cnt = 5 (5 个请求已发出, 响应未到) 同拍: handshake_done = 1 (新 PC 请求发出并握手, pnd_cnt_next = 5+1 = 6) 丢弃计数器初值 = pnd_cnt_next - handshake_done = 6 - 1 = 5 (丢弃 5 个响应 = 跳转前已发出的 5 个在途) 随后 5 拍: 每收到一个响应, discard_cnt -1 第 5 个响应到达后: discard_cnt = 0, 第 6 个响应 (新 PC 流的) 正常进入队列
设计智慧
不修改 IMEM 协议 (无需 abort 信号), 不引入复杂接口。只用 1 个 3 位计数器 + 1 个门控信号, 代价极低地实现了"忽略过期响应"。这是硬件设计中的常见模式: 与其撤回, 不如丢弃。

第十二课: 指令旁路与推测取指

什么是指令旁路?

当队列为空时, IFU 可以将 IMEM 返回的指令直接送到 IDU, 绕过队列写入-读出-再送的 1 拍延迟。此功能仅在 SCR1_NO_DEC_STAGE 宏开启时生效。

旁路类型枚举 (scr1_pipe_ifu.sv:108-115)

推测取指 (Speculative Fetch)

推测取指的含义
IFU 的 FSM 切换到 FETCH 后, 持续向 IMEM 发出请求 -- 指令是否真的被需要、是否会因分支预测失败而作废, IFU 不做判断。这是硬件级别的推测取指: 只要队列有空、在途未满、流水线未停, 就一直取。如果 EXU 判定分支错误, 通过 exu2ifu_pc_new_req_i 通知 IFU, IFU 清空队列 + 设置丢弃计数器, 然后从新地址重新取指。

两侧的地址生成差异

// 无 NEW_PC_REG: 新 PC 和正常取指合并为同一表达式
imem_addr_next = exu2ifu_pc_new_req_i ? exu2ifu_pc_new_i[XLEN-1:2] + handshake_done
                                       : imem_addr_ff          + handshake_done;

// 有 NEW_PC_REG: 新 PC 已寄存器化, 直接输出
imem_addr_next = exu2ifu_pc_new_req_i ? pc_reg[XLEN-1:2]
                                       : imem_addr_ff + handshake_done;
什么时候用?
SCR1 默认不开启此宏 (EAS 表 25: jump penalty = 1 cycle)。高频场景下可开启, 用 1 周期额外惩罚换取更高主频。
