第一课: IFU 模块全景

IFU 是什么?
IFU (Instruction Fetch Unit) 是 SCR1 流水线的第一级,职责是从指令存储器 (IMEM) 取指令,送给 IDU 译码。源码文件: src/core/pipeline/scr1_pipe_ifu.sv (826 行)。

第二课: IFU FSM -- 只有 2 个状态

// scr1_pipe_ifu.sv:91-94 -- 状态枚举
typedef enum logic {
    SCR1_IFU_FSM_IDLE,        // 不取指
    SCR1_IFU_FSM_FETCH        // 取指中
} type_scr1_ifu_fsm_e;
ifu_fetch_req ┌───────────┐ ──────────▶ ┌───────────┐ │ IDLE │ │ FETCH │ │ (不取指) │ ◀────────── │ (取指中) │ └───────────┘ ifu_stop_req └───────────┘ 
// scr1_pipe_ifu.sv:465-467
assign ifu_fetch_req = exu2ifu_pc_new_req_i & ~pipe2ifu_stop_fetch_i;
assign ifu_stop_req  = pipe2ifu_stop_fetch_i
                     | (imem_resp_er_discard_pnd & ~exu2ifu_pc_new_req_i);
3 种状态转移场景
(A) EXU 发出新 PC 请求 + 流水线没停 → IDLE→FETCH,开始取指
(B) 流水线停止信号拉高 → FETCH→IDLE,停止取指
(C) IMEM 报错,但丢弃计数器还没消化完 → FETCH→IDLE,等错误响应处理完
停止取指 ≠ 复位
pipe2ifu_stop_fetch_i 是来自流水线顶层的信号,在 Stall/Flush/调试暂停时拉高。IFU 回到 IDLE 后,队列也被清空 (q_flush_req=1),但已发出的 IMEM 请求不会收回 -- 靠丢弃计数器处理。

为什么半字粒度?

粒度RVC (16bit)RVI (32bit)
字粒度 (32bit)浪费 50% 空间刚好 1 槽
半字粒度 (16bit)刚好 1 槽占用 2 个连续槽
slot 0 slot 1 slot 2 slot 3 ┌──────────┬───┐ ┌──────────┬───┐ ┌──────────┬───┐ ┌──────────┬───┐ │ q_data[0]│err│ │ q_data[1]│err│ │ q_data[2]│err│ │ q_data[3]│err│ │ (16bit) │(1)│ │ (16bit) │(1)│ │ (16bit) │(1)│ │ (16bit) │(1)│ └──────────┴───┘ └──────────┴───┘ └──────────┴───┘ └──────────┴───┘
每槽 16 bit + 1 bit 错误标志 (来自 IMEM 响应)。4 个槽可以存储 2 条 RVI、4 条 RVC,或任意混编。

第四课: 队列读写与空满判定

写指针更新 (scr1_pipe_ifu.sv:384, 394)

assign q_wptr_upd  = q_flush_req | ~q_wr_none;           // L384
assign q_wptr_next = q_flush_req ? '0                    // L394: 清空归零
                                    : q_wptr       // 写 FULL(+2) 或 HI(+1)
                                      + SCR1_IFU_QUEUE_PTR_W'(q_wr_cnt);

读指针更新 (scr1_pipe_ifu.sv:399, 409)

assign q_rptr_upd  = q_flush_req | ~q_rd_none;           // L399
assign q_rptr_next = q_flush_req ? '0                    // L409: 清空归零
                                    : q_rptr       // 读 WORD(+2) 或 HWORD(+1)
                                      + SCR1_IFU_QUEUE_PTR_W'(q_rd_cnt);

空/满判定

条件公式
判空q_rptr == q_wptr
占用度q_ocpd_h = q_wptr - q_rptr (0~4)
剩余空间q_free_h = 4 - (q_wptr - q_rptr_next) (保守估计)
3 位指针 = 2 位地址 + 1 位圈数
例如指针值 3'b101: 圈数位 = 1,地址位 = 2'b01,表示第 2 圈的 slot 1。环形写指针超前读指针时,差值自己带圈数信息,不用额外标志位。

第五课: 指令类型译码 -- 6 种 instr_type

// scr1_pipe_ifu.sv:96-104 -- instr_type 枚举
typedef enum logic[1:0] {
    SCR1_IFU_INSTR_NONE,             // 无有效指令 (IMEM 响应无效)
    SCR1_IFU_INSTR_RVI_LO_NV,        // PC 未对齐,返回高 16 位 = RVI 低半
    SCR1_IFU_INSTR_RVC_NV,           // PC 未对齐,返回高 16 位 = RVC
    SCR1_IFU_INSTR_RVI_LO_RVI_HI,    // 对齐: 低 16=RVI 低半, 高 16=RVI 高半
    SCR1_IFU_INSTR_RVI_LO_RVC,       // 对齐: 低 16=RVI 低半, 高 16=RVC
    SCR1_IFU_INSTR_RVC_RVI_HI,       // 对齐: 低 16=RVC, 高 16=RVI 高半
    SCR1_IFU_INSTR_RVC_RVC,          // 对齐: 低 16=RVC, 高 16=RVC
    SCR1_IFU_INSTR_RVI_HI_RVI_LO     // 对齐: 低 16=RVI 高半, 高 16=RVI 低半
} type_scr1_ifu_instr_e;

RVI_HI_RVI_LO: 为什么高半在前?
当取指地址 addr[1:0] = 00 且低 16 位是 RVI ([1:0]=11) 时,指令的数据排布是 { 高 16 位, 低 16 位 },即高半 (bits[31:16]) 在低地址。硬件按地址递增顺序接收数据,所以先收到高半、后收到低半。

第六课: 跨边界 RVI 拼接

问题

字 N-1 字 N ┌─────────┬─────────┐ ┌─────────┬─────────┐ │ RVC │ RVI_LO │ │ RVI_HI │ RVC │ │ [15:0] │ [31:16] │ │ [15:0] │ [31:16] │ └─────────┴─────────┘ └─────────┴─────────┘ ↑ ↑ 这一半是 RVI 低半 这一半是 RVI 高半 需要记住,下次拼接 和上次记住的低半拼成完整指令

记忆寄存器 instr_hi_rvi_lo_ff (scr1_pipe_ifu.sv:320-322)

assign instr_hi_rvi_lo_next = (instr_type == SCR1_IFU_INSTR_RVI_LO_NV)
                             | (instr_type == SCR1_IFU_INSTR_RVI_LO_RVI_HI)
                             | (instr_type == SCR1_IFU_INSTR_RVI_LO_RVC);
三种情况都说明"这一轮返回的高 16 位是 RVI 的低半部分",需要记住,等下一轮 IMEM 返回时拼接。 新 PC 跳转时强制清零: 跨边界状态属于旧 PC 流,跳过无效。
为什么只有 RVI 跨边界?
RVC 只有 16 位,不会跨 32 位字边界。只有 32 位 RVI 指令可能被 32 位存储字切开:前半个 RVI 在字 N 的高 16 位,后半个在字 N+1 的低 16 位。

第七课: IMEM 接口与在途事务跟踪

请求生成 (scr1_pipe_ifu.sv:598, 603)

// 新 PC 请求 (SCR1_NEW_PC_REG 关闭时):
ifu2imem_req_o = (exu2ifu_pc_new_req_i       // 跳转请求当拍发出
                   & ~imem_pnd_txns_q_full    // 在途未满
                   & ~pipe2ifu_stop_fetch_i)  // 流水线未停止
               | (ifu_fsm_fetch               // FSM 在 FETCH 状态
                   & ~imem_pnd_txns_q_full    // 在途未满
                   & q_has_free_slots);       // 队列有空位

地址寄存器 (scr1_pipe_ifu.sv:237-248)

imem_addr_next = exu2ifu_pc_new_req_i ? exu2ifu_pc_new_i[XLEN-1:2] + handshake_done
                                      : imem_addr_ff          + handshake_done;

ifu2imem_addr_o = {imem_addr_ff, 2'b00};  // 输出字对齐地址

在途事务计数 (scr1_pipe_ifu.sv:267-269)

请求握手完成 → +1 收到响应 → -1 │ │ ▼ ▼ ┌───────────────────────────────┐ │ imem_pnd_txns_cnt (0~7) │ └───────────────────────────────┘ │ │ q_full=1? imem_vd_pnd_txns_cnt = 总数 - 丢弃数 → 用于队列容量预测

预测性空间检查 (scr1_pipe_ifu.sv:454)

q_free_w_next = (4 - (q_wptr - q_rptr_next)) >> 1;  // 下一拍的空闲字
q_has_free_slots = (q_free_w_next > imem_vd_pnd_txns_cnt);  // 够容纳在途响应?
用 q_rptr_next (下一拍读指针) 而非 q_rptr: 如果当前周期 IDU 在读取队列,队列空间会增加,但设计者选择保守 -- 假设读操作不发生,确保不会欠估计导致溢出。

第八课: 丢弃计数器 -- 不看他、不用他、不理他

为什么需要丢弃?

PC 跳转后,之前发出的 IMEM 请求还在回来的路上(在途)。这些"过期"的响应不能进入队列 -- 它们是旧 PC 流的指令。最简单的方案: 数一数有多少个在途,然后跳过这么多响应。

丢弃计数器的 3 个入口 (scr1_pipe_ifu.sv:569-587)

imem_resp_discard_cnt_upd = exu2ifu_pc_new_req_i           // PC 跳转
                          | imem_resp_er                    // IMEM 错误
                          | (imem_resp_ok & imem_resp_discard_req);  // 丢弃收到了一个

// PC 跳转时: 丢弃数 = 在途总数 - 同拍握手的补偿
imem_resp_discard_cnt_next = exu2ifu_pc_new_req_i  ? imem_pnd_txns_cnt_next - handshake_done
                            // IMEM 错误且尚未丢弃: 丢弃全部在途
                            : imem_resp_er_discard_pnd ? imem_pnd_txns_cnt_next
                            // 正在丢弃中: 每收到一个响应 -1
                            : imem_resp_discard_cnt - 1'b1;

有效响应被屏蔽 (scr1_pipe_ifu.sv:510, 590-591)

imem_resp_discard_req = |imem_resp_discard_cnt;             // 丢弃计数 > 0?
imem_resp_vd          = imem_resp_received & ~imem_resp_discard_req;  // 筛掉被丢弃的
imem_vd_pnd_txns_cnt  = imem_pnd_txns_cnt - imem_resp_discard_cnt;   // 有效在途
设计智慧
不修改 IMEM 协议 (无需 abort 信号),不引入复杂接口。只用 1 个 3 位计数器 + 1 个门控信号, 代价极低地实现了"忽略过期响应"。这是硬件设计中的常见模式: 与其撤回,不如丢弃。

第九课: 指令旁路机制

触发条件 (仅 SCR1_NO_DEC_STAGE)

当没有独立译码阶段时,IFU 可以绕开队列,直接把 IMEM 返回的指令送到 IDU:
旁路类型条件数据来源
BYPASS_RVC队列空 + 新指令为 RVCIMEM 高/低 16 位
BYPASS_RVI_RDATA队列空 + 新指令为完整 RVIIMEM 32 位数据
BYPASS_RVI_RDATA_QUEUE队列有 1 个半字 RVI 头 + 新指令可拼接IMEM 低 16 位 + 队首半字

旁路对队列写入的影响 (scr1_pipe_ifu.sv:345-367)

旁路成功后,不写队列。但跨边界类型(如 RVI_HI_RVI_LO)的部分半字仍需暂存:
instr_type无旁路写入有旁路写入
RVC_NV / RVI_HI_RVI_LOHI / FULLNONE
RVI_LO_RVI_HI / RVI_LO_RVC / RVC_RVI_HIFULLHI (只暂存高 16 位)

第十课: IDU 输出接口 -- 指令如何拼接?

指令拼接的 6 种来源 (scr1_pipe_ifu.sv:693-700)

// RVC 场景: 高 16 位补 0,低 16 位 = 队首
SCR1_BYPASS_RVC:  ifu2idu_instr_o = {16'b0, rdata_hi_or_lo};

// 旁路 RVI: IMEM 原始 32 位数据
SCR1_BYPASS_RVI_RDATA: ifu2idu_instr_o = imem2ifu_rdata_i;

// 旁路拼接: IMEM 低 16 位 + 队列留下的高 16 位
SCR1_BYPASS_RVI_RDATA_QUEUE: ifu2idu_instr_o = {imem2ifu_rdata_i[15:0], q_data_head};

// 队列 RVI: 队首+1 (高半) + 队首 (低半)
default: ifu2idu_instr_o = {q_data_next, q_data_head};

有效信号生成 (scr1_pipe_ifu.sv:658-675)

ifu2idu_vd_o = 1'b0;  // 默认无效
if (instr_bypass_vd & idu2ifu_rdy_i) begin
    ifu2idu_vd_o = 1'b1;              // 旁路有效 → 直接送出
end else if (~q_is_empty) begin
    if (q_head_is_rvi & (q_ocpd_h == 1))  // 队首 RVI 但只有 1 个半字
        ifu2idu_vd_o = 1'b0;             → 还不能送出,等另一半
    else if (q_head_is_rvi | (q_ocpd_h >= 2))
        ifu2idu_vd_o = 1'b1;             → 完整 RVI 或有足够半字
    else
        ifu2idu_vd_o = q_head_is_rvc | q_err_head;  → RVC 只要有就能送出
end

错误信息 (scr1_pipe_ifu.sv:67-69, 347)

信号含义
ifu2idu_imem_err_o指令访问异常 (IMEM 返回错误)
ifu2idu_err_rvi_hi_oRVI 高半取指错误: 队首(低半)正常,队首+1(高半)有错误标志
两个信号独立:err_rvi_hi 精确定位到 RVI 指令的高半部分出错,即使在 imem_err 为 0 的情况下也可能单独为 1。

第十一课: SCR1_NEW_PC_REG -- 频率 vs 惩罚的权衡

维度无此宏 (默认)有此宏
跳转首拍的请求发出同拍下一拍 (额外 1 周期)
IMEM 地址路径EXU→MUX→IFU→IMEM (长组合路径)寄存器→IFU→IMEM (短)
最高频率受限于 EXU→IMEM 组合路径更高
地址生成逻辑需补偿 handshake_done单一来源,更简洁
跳转惩罚1 周期2 周期

两侧的地址生成差异

// 无 NEW_PC_REG: 新 PC 和正常取指合并为同一表达式
imem_addr_next = exu2ifu_pc_new_req_i ? exu2ifu_pc_new_i[XLEN-1:2] + handshake_done
                                      : imem_addr_ff          + handshake_done;

// 有 NEW_PC_REG: 新 PC 已寄存器化,直接输出
imem_addr_next = exu2ifu_pc_new_req_i ? pc_reg[XLEN-1:2]
                                      : imem_addr_ff + handshake_done;
什么时候用?
SCR1 默认不开启此宏 (EAS 表 25: jump penalty = 1 cycle)。高频场景下可开启,用 1 周期额外惩罚换取更高主频。
